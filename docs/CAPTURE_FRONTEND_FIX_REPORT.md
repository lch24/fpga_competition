# 采集前端间歇性失败 —— 排查、修复与交接报告

日期：2026-10-15 ｜ 分支：`main` ｜ 基线：提交前 HEAD `cfc2525`
选定产物：`build/system/calibrated_view_top_P8d.sbit`（本机构建；`build/` 已被 `.gitignore`，**比特流不进仓库**）

---

## 1. 概述

**问题**：上板连拍 3 张"时好时坏"——失败时照片拍不出来、`LED7` 常亮，且**必须重新烧录**才能再试。特征：**同一上电周期内三张的成败一致，不同周期之间随机**（同一份比特流也一样）。

**结论**：故障在**相机前端（`pclk` 域）**。每行采样到的 HREF 宽度偶发地不等于 2×1280 个 pclk，行尾字节被拆散 ⇒ 该行少 1 个像素；这样的行累积到一定数量，整帧像素数不等于 1280×720 ⇒ 帧被作废 ⇒ 显示不 enable ⇒ `LED7`。属**物理/时序层面的临界现象**（每次配置抽一次签），**不是 RTL 逻辑缺陷**。

**处理**：不再依赖"整帧像素数精确"这一条判据，改为**逐行保证 1280 个像素**（偏短补齐、偏长截断）。现在偶发失败**在同一上电周期内重试即可成功，不再需要重烧**。

## 2. 采集错误的处理逻辑

全部在 **`pclk`（相机像素时钟）域内**完成，分三层。

### 2.1 行级（`camera_byte_unpack`）：保证每行恰好 1280 个像素

用 `left` = "本行还差多少个像素"（行起始装 1280，每发一个像素减 1）：

| 该行采样到的 HREF 宽度 | 行为 | 该行像素数 |
|---|---|---|
| 恰好 2×1280 个 pclk（正常） | 正常配对 | 1280 |
| **偏短**（末尾字节落单） | 计入"偏短行"普查；行末**补发**像素至 `left == 0`（补出的像素重复上一像素） | 1280 |
| **偏长** | `left == 0` 之后**多余字节直接丢弃** | 1280 |

实现要点：**"还差多少"只用一次或归约（`left != 0`）参与判断，不用宽比较器**——该判断位于 `pixel_valid` 的组合通路上，宽比较器会吃掉 `pclk` 域的建立裕量。

### 2.2 帧级（`video_capture_hmic`）：保证帧计数不超过 TOTAL

`count` 只在 `< TOTAL` 时自增并打包；达到 TOTAL 后多余像素直接丢弃（不计数、不打包、不写 DDR）。**第 TOTAL 个像素照常打包**，所以前 TOTAL 个像素的内容与改动前逐位相同。

### 2.3 帧尾：输出诊断码，供上位机定性

按固定优先级给出一个 8 位码：

| 码 | 含义 |
|---|---|
| `0x00` | 干净帧 |
| `0x81` | 像素偏少，且**没有任何一行偏短**（帧边界问题） |
| `0x82` | 像素偏多 |
| `0x83` | 像素数正确，但末字未对齐 |
| `0x84` / `0x85` | 写 FIFO 丢 1 个 / ≥2 个打包字 |
| `0x8B` / `0x8C` / `0x8D` | 偏短的行数为 1~3 / 4~15 / ≥16 |
| `0x86` | 其它 |
| `0x80` | **流程层**：相机未就绪（按键过早），非采集失败 |

**优先级顺序**：偏多 → FIFO 丢字 → 偏少（再按偏短行数分级）→ 末字未对齐 → 其它。
这样分层后，`0x81` 一旦出现即可信地证明"**没有丢字**"，把嫌疑锁定在相机前端；`0x8B~0x8D` 则直接给出"有多少行的像素数不等于 1280"，把问题定位到"行"这一级。

## 4. 已被排除的方向（**不要再重复验证**）

| 曾经的怀疑 | 排除依据 |
|---|---|
| 打包 / 写 FIFO / push 握手 / DDR 写入链路 | 丢字码 `0x84/0x85` **从未出现**；失败帧的写入字数差与像素差**严格 16 倍** |
| 核心域时序违例 / 资源不足（`ddrphy_sysclk` 等） | 故障整链在 `pclk` 域；核心域违例在**好周期与坏周期同样存在** |
| 操作时序（拍照/烧录间隔、配置完成到首次拍照的时间） | 对 60 个上电周期做过时间间隔统计，失败组与干净组**分布高度重叠**；并有"几乎同一时刻按键、一成一败"的直接对照 |
| 上电瞬间相机链路抖动 | 失败帧期间 `camera_seen` 恒真、`health_bits` 稳定、`rx_errors=0` |
| 输入**保持裕量**不足（输入延迟 / IOB 输入寄存器） | 用"把 `set_input_delay -min` 调到悲观测值、逼 P&R 做 hold-fix"实测证伪：**失败率无变化** |
| 只靠"消除引脚直连组合路径" | 等深度输入寄存 + 帧边界寄存都做过，**有用但不足以归零** |
| I2C 配置域 CDC 违例是主因 | 加 false path 后该违例清零，**失败率不变** |
| 必须先做资源释放（P3）才能修本问题 | 本问题在 `pclk` 域，P3 释放的是别处资源，**对根因无用** |
| `0x8D`（≥16 行偏短）可直接当定位依据 | 第一版行普查是**伪影**：在捕获模块里用"本模块寄存的 href"与"解包器输出的 pixel_valid"比较，行末像素落在 href 拉低之后 ⇒ **每行都读成 1279**、计数每帧饱和。**移入解包器、改在 `emit` 周期计数后才可信** |

## 5. 继续工作要注意什么

1. **器件已满**：CLMA / CLMS 均约 100%、LUT 99%。**新增逻辑前先评估能否布通**。
2. **`pclk` 域裕量窄且抖动**：`cmos2_pclk → cmos2_pclk` 的建立裕量随 P&R 在约 1 ~ 3.4 ns 之间波动，**每次构建都要复核这条路径**。教训：把 12 位比较器串进 `pixel_valid` 通路会立刻在该域产生新违例，后用"或归约 + 下行计数器"才恢复。
3. **诊断码不能用来报告"非致命异常"**：`video_board_flow` 把任何非零 `cap_status` 都当失败。想报告"可接受但值得知道的异常"，只能另开**调试页字段**。
4. **完整性判定必须在 `pclk` 域内完成**，不要搬到 core 域。
5. **一个未解风险**：本版策略是"保留前 TOTAL 个像素"。若多余像素出现在**帧中段**，会让后半幅图像前移、末尾被截掉，而该帧仍被判为干净并发布。多余像素**只能来自"帧窗口内数到的行数超过 720"**（行内已被封顶）；现有现象与"多余在帧尾"一致，但**未证明**。
6. **硬件侧优先确认**：该摄像头在厂商自带例程下也"飘细细的彩线"，DVP 物理链路/传感器边缘抖动很可能是这些临界相位的来源。建议先换排线/摄像头、检查供电与地。

## 6. 后续可做

1. **打通标定**：按下标定后报 `status=2`（`NO_BOARD`，检测器未找到足够标定点，属算法/光学侧；那两个周期的照片本身是干净的）。先让标定板清晰占满视野复测；仍报 2 则用 `uart_monitor.py COM14 --corners` 导出角点定位。
2. **让"修剪量"可观测**：把本次修剪的像素数接到调试页的一个空闲字段，用来判定多余像素在**帧尾还是帧中段**（据此决定是否需要回到"拒绝"策略）。字段位置需先核对 `rtl/debug/debug_snapshot.v`。
3. **资源释放（P3）**：`board_display_hmic` 的 4096 FF 大 mux → BRAM 行缓冲；`hdmi_pixel_bridge` 的 LUTRAM FIFO → BRAM。**先腾空间，再做优化。**
4. **三项指标基线**（分辨率 / 延时 / 资源）：分辨率由 `WIDTH/HEIGHT` 参数与串口 `video` 计数读取；延时每帧的 `last_remap_ms` 已可从串口读出；资源取每次构建的 Device Utilization。
